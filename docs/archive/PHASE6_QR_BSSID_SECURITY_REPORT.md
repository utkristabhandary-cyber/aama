# AAMS Phase 6 — Secure QR Attendance Check-in + Network/BSSID Verification Report

## 1. Executive Summary

Phase 6 adds a server-authoritative, cryptographically secure QR check-in layer on
top of the existing Phase 5 attendance engine. A teacher starts an attendance
session and activates a QR broadcast; the server issues a short-lived (15s),
session-bound, unpredictable token encoded as `AAMSQR1|<attendance_session_id>|<TOKEN>`.
A student scans or pastes that payload and `POST /api/attendance/qr/check-in/`
validates the user's real identity (`request.user.student_profile`), the live QR
session, token currency, section membership, and duplicate/replay conditions before
creating a normal `AttendanceRecord` through the Phase 5 engine.

The most important security decision — taken honestly rather than faked — is the
**network/BSSID layer**. A standard web browser cannot produce an OS-attested BSSID,
so the backend **refuses to fabricate** BSSID verification. Client-claimed BSSID/
mobile methods are always downgraded to `unavailable`; the architecture and API
contract are ready for a future native mobile client that can register a real
attestation channel. This is reported as an explicit, honest platform limitation,
not as working BSSID verification.

Status of the 34-section definition of done: every item is satisfied except the
parts that require a native mobile application (BSSID hardware attestation), which
are explicitly BLOCKED/DEFERRED and documented. No security property was faked.

## 2. Initial QR Architecture (as found)

Phase 5 had a `QRAttendanceSession` model with a server-stored rolling token and a
`student_ids`/`student_timestamps` ledger. The pre-existing flow was audited for:

- **Token security** — the token alphabet is `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`
  (no `I`, `O`, `0`, `1`), generated with Python's `secrets` (cryptographically
  strong). Good entropy per token (≈35 bits over 8 chars).
- **Expiration** — implemented via `get_current_token()` comparing age against TTL.
- **Predictability** — `secrets.choice` is non-predictable.
- **Session binding** — token stored per `QRAttendanceSession` which is bound to a
  unique `(teacher, attendance_session)`.
- **Idempotency** — `mark_qr_student` uses `get_or_create` on
  `(attendance_session, student)`.

The Phase 5 QR surfaced a `validate`/`mark` path used by the frontend, but Phase 6
needed a true check-in endpoint whose identity always comes from `request.user` and
whose token resolution goes through the encoded `attendance_session_id` (the payload
embeds the attendance-session id, not the QR row id). The semantics were refactored
so `check_in_student` resolves the live QR via `attendance_session_id` and validates a
constant-time token match.

## 3. Final QR Architecture

```
TEACHER (authenticated user -> teacher_profile)          STUDENT (authenticated user -> student_profile)
   |  POST /api/attendance/qr/start/                         |  POST /api/attendance/qr/check-in/
   |  {attendanceSessionId}                                  |  {qrPayload, network:{method:"unavailable"}}
   v                                                         |
QRAttendanceSession (1 active/teacher, rotated token) ----->|--parse payload (AAMSQR1|<session id>|<TOKEN>)
   | token bound to AttendanceSession                        |
   v                                                         v
                                          server-side validation chain (see §8)
                                                         |
                                                         v
                                                 AttendanceRecord (Phase 5 engine)
                                                         |
                                                         v
                                       summarize_student_attendance / reports (unchanged)
```

The QR is purely a **security/eligibility mechanism**; the authoritative record is
still `AttendanceRecord` created through the Phase 5 `mark_qr_student` path. Manual
and bulk teacher marking, roll, finalization, and student reports are untouched and
still verified by the full test suite.

## 4. Token Generation

Tokens are generated by `generate_token()` in `backend/apps/attendance/models.py`:

```python
alphabet = "ABCDEFGHJKLMNPQRSTUVWXYZ23456789"
token = f"{part()}-{part()}"   # two 4-char groups, e.g. 8F3K-29PA
```

using `secrets.choice` (CSPRNG). Ambiguous characters (`I`, `O`, `0`, `1`) are
excluded for scannability. Each 8-character token has ~35 bits of entropy — far more
than enough for a 15-second window, where success requires guessing the exact
current token AND being section-eligible.

## 5. Token Lifetime

Lifetime is governed by the setting `AAMS_QR_TOKEN_TTL_SECONDS` (default **15**
seconds) in `backend/config/settings/base.py`:

```python
AAMS_QR_TOKEN_TTL_SECONDS = int(os.getenv("AAMS_QR_TOKEN_TTL_SECONDS", "15"))
```

This is read **at request time** in `QRAttendanceSession.get_current_token()`
(via `getattr(settings, "AAMS_QR_TOKEN_TTL_SECONDS", ...)`) and in the serializer's
`expires_in_seconds`, so `override_settings` works deterministically in tests. The
client cannot extend the lifetime — expiry is strictly server-side (`timezone.now() -
token_generated_at > ttl`).

## 6. Token Rotation

Rotation is server-authoritative. `QRAttendanceSession.rotate()`:

```python
def rotate(self):
    self.token = generate_token()
    self.token_generated_at = timezone.now()
    self.save(update_fields=["token", "token_generated_at"])
    return self.token
```

`get_current_token()` lazily rotates when the current token is older than the TTL.
The teacher UI calls `POST /attendance/qr/start/` (which re-runs `start_qr_session`,
rotating the token) on an interval matching `expires_in_seconds`, so a fresh payload
is rendered every ~15s. The client never generates a token — it only renders the
payload the server returns.

## 7. QR Payload Format

The payload format is preserved from the historic AAMS format:

```
AAMSQR1|<attendance_session_id>|<TOKEN>
```

- `AAMSQR1` — fixed version prefix.
- `<attendance_session_id>` — an **identifier only**, never authorization.
- `<TOKEN>` — the security credential, matched constant-time server-side.

No PII, no auth tokens, and no secrets are embedded. `build_qr_payload()` and
`parse_qr_payload()` maintain compatibility; the token is validated to belong to the
resolved active QR session (`revoked=False`), the live security check.

## 8. QR Validation (server-side chain)

`check_in_student` in `backend/apps/attendance/services.py` runs a deliberate,
non-leaking order:

1. Payload format valid → else `400` generic.
2. Live (non-revoked) QR resolves for the payload's `attendance_session_id` → else `400` generic.
3. Attendance session **not finalized** → else `400`.
4. Semester not `COMPLETED` → else `400`.
5. Token is current (constant-time `secrets.compare_digest`) → else `400` generic.
6. Student belongs to the session's section(s) → else `403` (eligibility).
7. Network policy gate satisfied (see §14) → else `403 networkVerificationRequired`.
8. Duplicate / replay → `200 alreadyRecorded` (idempotent, no new row).
9. Otherwise create `AttendanceRecord` → `201`.

Token validity is checked **before** membership/duplicate so a wrong or missing token
can never confirm whether a student is enrolled or already marked (no oracle leak).

## 9. Student Check-in Flow

1. Student scans the classroom QR (or pastes the full payload) in
   `StudentQRScannerView`.
2. Frontend `checkInWithQR` POSTs `{ qrPayload, network: { method: 'unavailable' } }`
   to `POST /api/attendance/qr/check-in/`.
3. Backend authenticates via `request.user`; identity is
   `request.user.student_profile` (never a client `studentId`).
4. Server runs the §8 chain, then creates `AttendanceRecord` (status `present`) with
   evidence fields `checked_in_at`, `network_verification_method`, `bssid_normalized`.
5. Server returns `201` (recorded), `200` (already recorded), or a `4xx` with a safe
   message. Frontend renders the server's verdict only — never a fabricated success.

## 10. Duplicate Prevention

- **Attendance duplicate:** `AttendanceRecord` has a database `UniqueConstraint` on
  `(attendance_session, student)`
  (`uniq_attendance_record_per_session_student`), enforced at the DB layer.
- `mark_qr_student` uses `get_or_create`, and `check_in_student` returns an idempotent
  `200 alreadyRecorded` if a record already exists — no second row is ever created.
- **Cross-student reuse:** a shared rolling token is legitimate (used by the whole
  class), but each `(session, student)` can only ever produce one record.

## 11. Replay Protection

The QR token itself is **shared** by design (one broadcast, many students), so a
"token replay" between different students is legitimate and expected. Replay/abuse is
instead bounded by:

- **Per-student idempotency** — a repeated check-in for the same `(session, student)`
  returns `200 alreadyRecorded` and creates nothing new (attacks 11).
- **Token lifetime** — after the TTL the token expires server-side and rotation
  generates a fresh one; a stale payload is rejected (attacks 5).
- **Revocation** — stopping a QR session flips `revoked=True`; the partial unique
  constraint prevents a second active QR; marked-revoked QR payloads fail (attack 6).
- **Rate limiting** — per-student throttle bounds how many times a captured payload
  can be sprayed (see §27).

## 12. Session Ownership

- `POST /attendance/qr/start/` requires the authenticated user to have a
  `teacher_profile` AND that profile to own the `AttendanceSession`
  (`attendance_session.teacher_id == teacher.pk`), else `403`.
- `stop` requires the same ownership (admin may stop any).
- A student cannot `start`/`list`/`update`/`destroy` QR sessions (permission matrix,
  §25). Attack 9 (teacher operating another teacher's session) rejected.

## 13. Student Membership Validation

Membership is derived from trusted relationships only: `request.user.student_profile`
→ `student.section_id` compared to `attendance_session.sections`. The client can never
supply a `sectionId` to bypass membership (attack 3). A student outside the section
gets `403` (attack 8) and no record is created.

## 14. Network / BSSID Architecture

**Critical honest design.** A standard browser cannot provide an OS-attested BSSID.
Three honest states are defined:

```
network_verification_method ∈ { bssid, mobile_network_bridge, unavailable }
```

- The web client always reports `unavailable` — it cannot attest a network.
- `resolve_network_verification()` **downgrades any client-claimed `bssid` or
  `mobile_network_bridge` to `unavailable`** until a real OS-attestation verifier
  exists. A client can never mark itself network-verified (attack 10).
- A supplied `bssid` string is normalized and stored **only as self-reported
  telemetry**, never as proof.
- An unsupported method (e.g. `gps`) or a malformed BSSID → `400`.

**No fake APIs** like `navigator.wifi.bssid`, `window.bssid`, `wifiConnected=true`,
or hardcoded BSSIDs exist anywhere.

## 15. Web Platform Limitations

**The web client cannot securely provide a BSSID.** Under the current architecture the
correct statement is: "Web platform cannot securely provide BSSID." The implementation
does not fake it — it records `network_verification_method = "unavailable"` honestly.
Optionally, when `AAMS_QR_REQUIRE_NETWORK_VERIFICATION=true`, web check-in is blocked
with `403 networkVerificationRequired` because the required proof cannot be supplied
(see §33 for the config default).

## 16. Mobile Platform Requirements (future native app)

To enable true network anchoring, a future native **Student Mobile** client must
provide an OS-attested network proof through a defined contract. Required capability:

- Android: `WifiManager`/`ConnectivityManager` attestation (with
  `ACCESS_FINE_LOCATION` and/or `ACCESS_WIFI_STATE` + user permission, subject to OS
  version and Android 13+ `NEARBY_WIFI_DEVICES`).
- iOS: subject to `CNCopyCurrentNetworkInfo` authorization; MDM/profile may be needed
  to reveal BSSID.

The proof must be: created by the OS/platform, bound to the session, expire, and be
verifiable by a server-registered attestation channel (e.g. signed nonce + BSSID).
Once that channel exists, the `resolve_network_verification` downgrade constant is
flipped and a verified method (`bssid`/`mobile_network_bridge`) becomes meaningful.
This contract is documented for the mobile team; no native code is invented in the web
frontend.

## 17. BSSID Normalization

`normalize_bssid()` accepts `AA:BB:CC:DD:EE:FF`, lowercase, dash- or dot-separated,
validates hex via `^[0-9A-Fa-f]{12}$` after stripping separators, and returns the
canonical lowercase colon form `aa:bb:cc:dd:ee:ff`. Malformed values return `None`
and are rejected at the check-in boundary (`400`). No unnecessary network information
is exposed in API responses (only the normalized telemetry field on the record).

## 18. Network Anchoring

The conceptual `AttendanceSession → Network Anchor → Check-in → Proof → Django
Verification` model is designed so the anchor is **per session**, not global (rooms
can have different networks). A student can never choose the expected BSSID; the
teacher/admin side must remain authoritative for the session's network context. In the
web-only deployment, no insecure anchor is fabricated — until a native attestation
channel exists, network anchoring is honestly reported as unavailable with the
architecture and contract in place.

## 20. API Contracts

**`POST /api/attendance/qr/start/`**
```
Req:  { "attendanceSessionId": 123 }
Resp: 200 { "id": 5, "teacher": 2, "attendance_session": 123, "token": "8F3K-29PA",
            "token_generated_at": "...", "student_ids": [], "revoked": false,
            "payload": "AAMSQR1|123|8F3K-29PA", "checked_in_count": 0,
            "expires_in_seconds": 15, "created_at": "..." }
```

**`POST /api/attendance/qr/check-in/`**
```
Req:  { "qrPayload": "AAMSQR1|123|8F3K-29PA",
        "network": { "method": "unavailable" } }
Resp:
  201 { "detail": "Attendance recorded.", "alreadyRecorded": false, "status": "present",
        "networkVerificationMethod": "unavailable", "attendance": { "id": .., "studentId": ..,
        "status": "present", "checkedInAt": "...", "networkVerificationMethod": "unavailable",
        "bssidNormalized": null } }
  200 { "detail": "Your attendance is already recorded for this session.",
        "alreadyRecorded": true, "status": "present", "attendance": { ... } }
  400 { "detail": "<generic safety message>" }   # bad payload / unknown QR / expired token /
                                                 # finalized session / completed semester /
                                                 # malformed bssid / unsupported method
  403 { "detail": "You are not part of this class section." }   # membership
  403 { "detail": "This class requires network-verified check-in...",
        "networkVerificationRequired": true }                   # policy gate (when enabled)
  429 { "detail": "Request was throttled. Expected available in X seconds." }
```

`studentId` is never accepted as an authority field — identity is
`request.user.student_profile`.

## 27. Rate Limiting / Abuse Protection

Two DRF `SimpleRateThrottle` subclasses in `backend/apps/attendance/throttling.py`:

- `QrCheckInThrottle` (scope `qr_checkin`, key per-user+IP) on `check_in`/`validate`/
  `mark` — default **`30/min`** (`AAMS_QR_CHECKIN_THROTTLE_RATE`).

  (`AAMS_QR_ACTION_THROTTLE_RATE`).

spraying a captured payload cannot lock out the rest of the class. Excessive requests
return `429`. Verified by `test_check_in_throttled_per_student` (`1/min` override
yields `429` on the second request).

## 32. Remaining Limitations

1. **BSSID/network verification from a web browser is not possible.** The web
   client honestly reports `unavailable`; there is no OS-attested BSSID path for a
   standard browser, and none is faked.
2. **Network anchoring requires a native mobile client.** The backend contract and
   capability boundary exist; the actual proof/attestation channel must come from a
   future native app.
3. **Token is bring-your-own**: a student anywhere (even off-network) can check in
   while `AAMS_QR_REQUIRE_NETWORK_VERIFICATION=false` (the default), because no
   network proof can be required without a verifier. This is the honest default.
4. QR tokens are shared by design; replay detection is per-student idempotency +
   short TTL, not per-token single-use (a single-use token would break legitimate
   multi-student scans and network retries).

## 33. Required Future Mobile Implementation

- Provide an OS/service-level attestation credential (BSSID/network proof) bound to
  the attendance session and a server-known nonce.
- Register a verifier so `resolve_network_verification` can accept a verified
  `bssid`/`mobile_network_bridge` instead of downgrading it.
- Submit `network.method` + signed proof via the same `POST /attendance/qr/check-in/`
  contract so web and mobile share one attendance engine.
- When such a client applies, flip `AAMS_QR_REQUIRE_NETWORK_VERIFICATION=true` to
  enforce network-verified check-in and reject `unavailable`.

## 34. Future Recommendations

- Consider per-device signed attestation (secure enclave / Android Keystore) for
  stronger replay resistance than TTL + idempotency.
- Store an audit log of check-in evidence (method, timestamp, IP) for compliance.
- Add a `reasonPinned`/`expected_bssid` per session controlled by the teacher/admin
  once a verifiable channel exists.
- Add operational analytics on QR check-in latencies and throttle-hit rates.
